# spin_gnn

Self-supervised graph-neural-network next-token prediction on the disordered
kinetic Ising spin model of Zavatone-Veth & Pehlevan, "A note on the dynamics
of extended-context disordered kinetic spin models" (2026),
https://doi.org/10.1088/1751-8121/ae38a4.

## The physical model

The paper's dynamics is, for context length `K` and inverse temperature `beta`:

```
p(s_t | s_{t-1},...,s_{t-K}) ∝ exp[-beta * E],   E = - s_t^T sum_{k=1}^K J_k s_{t-k}
```

with `{J_k}` jointly Gaussian, zero-mean, `E[J_ij,k J_i'j',k'] = delta_ii' delta_jj' Gamma_kk'`
(uncorrelated across sites, correlated across lags via `Gamma`). This is
already a next-token-prediction process: `s_t` (the full spin configuration
at "time" `t`) is the next token, conditioned on a context window of `K`
previous tokens, generated by an all-to-all disordered coupling structure. We
implement the **Ising** variant (`s in {-1,+1}^N`), for which the energy is
linear in `s_t` and the conditional factorizes exactly per site:

```
h_t,i = sum_{k=1}^K sum_j J_k[i,j] s_{t-k,j}         (local field, = a linear graph convolution)
p(s_t,i = +1 | context) = sigmoid(2 * beta * h_t,i)  (exact, closed form)
```

This gives an exact Bayes-optimal reference to benchmark any learned model
against -- see "Exact-recovery sanity check" below.

**Scaling assumption.** The paper states the coupling covariance without an
explicit `N` dependence. For the `N -> infinity`, fixed `(T, K)` limit they
study to have an `O(1)` local field, couplings must be Sherrington-Kirkpatrick
scaled: `Var(J_ij,k) = Gamma_kk / N`. That's what's implemented
(`DisorderConfig.coupling_scale`, default 1.0, applied as `coupling_scale/sqrt(N)`).
Set `coupling_scale` and `n_spins` together if you want to match a
non-extensive convention instead.

**Lag correlations `Gamma_{k,k'}`** (`DisorderConfig.gamma_kind` / `gamma_param`,
`simulate.build_gamma`): `"identity"` (uncorrelated lags, the default),
`"alternating"` (the paper's alternating-sign example), or `"power_law"`
(`Gamma_{k,k'} = |k-k'|^-gamma_param` off-diagonal, `1` on-diagonal -- a
long-range lag-correlation ansatz used for the context-length scaling sweep
below). The raw power-law Toeplitz matrix isn't guaranteed PSD for every
`(gamma_param, K)`, so it's projected to the nearest PSD matrix (clipped
eigenvalues) before use.

## Mapping onto the GNN

- **Nodes** = the `N` spins.
- **Edges** = the (possibly randomly sparsified) couplings `J_k`; the true
  model is fully-connected, which is the reason sparsification is worth
  studying -- a dense `O(N^2 K)` graph doesn't scale.
- **Node representation** has dimension `2 + H`: **2 visible directions**
  carrying the physical up/down spin information (the network's read-in for
  the true one-hot spin state), plus **H additional hidden directions**
  (`ModelConfig.hidden_dim`, default 32) the network can use for anything the
  bare linear mean field doesn't capture -- most relevantly, compensating for
  information lost to sparsification.
- **Self-supervised objective**: next-token prediction over the 2-symbol
  vocabulary `{down, up}`, cross-entropy against the realized next spin at
  every node, using only the spin trajectory itself (no external labels).

## Random sparsification

`spin_gnn/graph.py` keeps each directed edge of the coupling graph
independently with probability `keep_prob`, optionally rescaling surviving
edges by `1/keep_prob` to preserve `E[edge weight]` under the sparsification
ensemble (the usual dilute-spin-glass / inverse-propensity compensation).
`spin_gnn/sparsify.py` sweeps `keep_prob` against a *fixed* set of disorder
realizations and trajectories, training an independent model at each level
and reporting validation accuracy and NLL-gap-to-Bayes-optimal, so you can see
how much of the exact local field's information a sparsified GNN can still
recover (and whether the hidden directions or extra layers help it do so).

## Context-length / data scaling sweep

`spin_gnn/scale_sweep.py` trains one model per `(context_length,
n_train_sequences)` grid point and reports the minimum test NLL reached over
training, evaluated against a *held-out* pool of disorder realizations never
seen in training (`train.train_model(cfg, test_windows=...)`), not just a
time-split suffix of the training trajectories -- so the result reflects
generalization across the disorder ensemble. The held-out pool is seeded from
`context_length` alone, so every `n_train_sequences` point at a given
`context_length` is scored against the *same* test pool, and training
realizations are seeded contiguously so a smaller training set is a literal
prefix of any larger one at the same `context_length` -- both reduce
cross-point variance when comparing across the sweep.

`scripts/slurm/scale_sweep.sbatch` runs this as a Slurm array job (one task
per grid point) and `spin_gnn/aggregate_scaling.py` concatenates the resulting
per-task CSVs into one table for fitting/plotting.

**Transformer baseline.** `spin_gnn/transformer_baseline.py` (`SpinTransformer`)
is a standard `nn.TransformerEncoder` (nhead=1, no causal mask -- the K-lag
window is a fixed-size non-autoregressive context, unlike the k-SAT trace
below) over the same next-spin-prediction task, but with **no access to the
true coupling graph** `J` -- it sees only the raw K-lag spin trajectory and
must discover any useful structure purely from self-attention, isolating the
value of SpinGNN's privileged structural input. `transformer_scale_sweep.py`
mirrors `scale_sweep.py`'s grid/held-out-pool construction exactly but trains
`SpinTransformer`, with `find_matching_d_model` choosing `d_model` so its
parameter count matches SpinGNN's at that `context_length` -- a
capacity-controlled comparison, not just "bigger vs. smaller."
`spin_gnn/bayes_accuracy.py` computes the Bayes-optimal accuracy ceiling
(thresholding the *true* analytic posterior at 0.5) per
`(gamma_kind, gamma_param, context_length)`, independent of
`n_train_sequences` or model type, as the reference line both scaling sweeps
should approach from below.

## Approximate message passing (AMP) for teacher-student inference

A separate exploration of the same disordered kinetic Ising model
(`spin_gnn/amp.py`): rather than training a GNN/transformer, run
**approximate message passing** directly on the teacher's own generative
model to infer the couplings `J` from an observed trajectory, and compare
against the naive MAP estimate. `spin_gnn/amp_sweep.py` sweeps the sample
ratio `alpha = T_total / N` and records both estimators' reconstruction
error and held-out NLL gap to the teacher (`scripts/slurm/amp_sweep.sbatch`,
output under `amp_results/`). `tests/test_amp.py` covers the AMP update
equations; `scripts/_amp_diagnose.py` is a standalone diagnostic for
inspecting convergence on a single instance.

## Exact-recovery sanity check

`tests/test_exact_recovery.py` builds `SpinGNN(hidden_dim=0, num_layers=1,
exact=True)` on the full (`keep_prob=1.0`) graph and asserts its output
exactly reproduces the closed-form posterior above. Run this after touching
`graph.py` or `model.py`, before trusting any training result -- it's the
one thing that must hold regardless of what's learned elsewhere.

## k-SAT unit-propagation trace exploration

A second, self-contained exploration in this repo (`spin_gnn/ksat.py` and
friends): does next-token prediction learn to reproduce the *dynamics of
combinatorial search*, not just a physical process? Random k-SAT instances
are solved with a textbook DPLL unit-propagation solver using a
most-constrained-variable (MCV) branching heuristic, and the solver's
execution trace is emitted as a sequence of numeric vector tokens -- that
trace is what a transformer is then trained on via next-token prediction.

**Instances.** `sample_random_ksat` (`SATConfig`: `n_vars`, `k`, `alpha`)
draws `m = round(alpha * n_vars)` random k-clauses over `n_vars` variables,
each clause picking `k` distinct variables uniformly at random with an
independent random sign. `alpha=4.2` (the default) sits near the classic
random-3-SAT satisfiability threshold (~4.267), so a batch of sampled
instances is a mix of SAT and UNSAT rather than trivially one or the other.

**Solver.** `solve_with_trace` is plain chronological-backtracking DPLL, no
clause learning or watched literals -- deliberately the simple textbook
algorithm, since the point is observing unit-propagation/backtracking
dynamics at toy sizes, not building a competitive solver. At each step
(every point the assignment changes: a unit-propagation assignment, a
branching decision, a branch flip, or a backtrack pop) it emits one
**variable-values token** followed by one **clause token** per currently
non-trivial (not yet satisfied) clause. Every token is a vector in
`R^{n_vars+1}`:

- dims `0..n_vars-1`: variable-values token = current assignment per
  variable (`-1`=False, `0`=unassigned, `1`=True); clause token = `-1`/`1`
  if the variable appears negated/positive in that clause, `0` if it's
  absent *or* if it appeared but has since been falsified by the current
  assignment (falsified literals are zeroed out as soon as they're
  falsified -- a **reduced** clause encoding, not the clause's fixed
  original pattern).
- dim `n_vars`: `-1` for a variable-values token, `+1` for a clause token.

Backtracking is tracked as metadata (`events`, one entry per step, `kind` in
`{"unit_prop","decision","flip","backtrack"}`) for the statistics analysis
below, not as a third token dimension -- only a decision fully exhausted in
both directions counts as a "backtrack"; retrying a decision's other value
is a "flip", not a backtrack past it.

`spin_gnn/sat_stats.py` samples many random instances from a `SATConfig`,
solves each, and reports/saves per-instance trace statistics (SAT/UNSAT
split, number of decisions/unit-propagations/backtracks, max decision depth,
trace length) -- the actual "statistics of the unit-clause analysis" pass.

`spin_gnn/sat_transformer.py` (`SATTransformer`) is a causal
(`generate_square_subsequent_mask`-masked) transformer over these vector
tokens -- genuinely autoregressive across the whole trace, unlike
`SpinTransformer`'s fixed-window non-causal case -- with a per-dimension
3-way (`{-1,0,1}`) classification readout. `spin_gnn/train_sat_transformer.py`
trains it via next-token prediction over `spin_gnn/sat_dataset.py`'s
variable-length-trace dataset (traces are padded per batch since they don't
share a fixed length the way the spin model's K-lag windows do), and reports
`val_satisfying_completion_rate`: on held-out SAT instances, teacher-force
the model on the trace up through the second-to-last token and check whether
its single greedy next-token prediction is itself a satisfying assignment --
the "did it learn to reach a correct answer" metric, distinct from (and a
much higher bar than) token-level next-token accuracy.

**Hyperparameter sweep findings** (`spin_gnn/sat_hparam_sweep.py`,
`scripts/slurm/sat_hparam_sweep.sbatch` + `sat_nhead_sweep.sbatch`, both at
10,000 training instances / 15 epochs): a `(d_model, nhead)` grid over
`{32,64,128,256} x {1,2,4}` found only `d_model=256` beat the majority-class
baseline (89.05%) by a meaningful margin, but `val_satisfying_completion_rate`
stayed exactly 0% everywhere -- raising the question of whether single/few
-head attention was the bottleneck rather than model width. A follow-up scan
fixing `d_model=256` and extending `nhead` to `{1,2,4,8,16,32}` (all valid
divisors of 256) found: per-token accuracy and test NLL improve monotonically
from `nhead=1` to `nhead=8` (92.6% -> 93.7%, the sweep's best config overall),
then *worsen* at `nhead=16` (89.6%, barely above baseline) before partially
recovering at `nhead=32` (90.9%) -- all three of `nhead={1,2,4,8}` still show
exactly 0% `val_satisfying_completion_rate`, while `nhead=16` and `nhead=32`
are the *only* configs in the whole sweep with a nonzero completion rate
(0.7% and 1.4% respectively), despite their worse raw accuracy/NLL. Every
`nhead>=8` config's `best_epoch` lands on the very last training epoch, so
this may reflect under-training at higher head counts (more epochs needed to
converge) rather than a genuine capacity ceiling -- a natural next step
rather than a settled answer. See `notebooks/sat_unit_propagation_results.ipynb`
section 3b for the full plot.

A second follow-up (`sat_mlp_sweep.sbatch`) fixed `d_model=256, nhead=8` and
scanned `num_layers` ("number of MLPs" -- each transformer block is one
attention sub-layer plus one feedforward/MLP sub-layer) in `{1,2,4,6}`
against `dim_feedforward` (each block's own MLP hidden width, previously
always the implicit default `4*d_model=1024`) in `{256,512,1024,2048}`:
`num_layers=1` is too shallow (collapses to baseline everywhere) and
`num_layers=6` with `dim_feedforward>=1024` fails to train at all
(`best_epoch=0`, likely needs LR warmup at that depth); the best config
found in the whole notebook is `num_layers=4, dim_feedforward=1024`
(accuracy ~94.3%, NLL ~5.0), but `val_satisfying_completion_rate` is exactly
0% for all 16 of these configs -- scaling depth/MLP width improved the
easier per-token metric without recovering any of the head-count sweep's
(small) ability to actually complete a satisfying assignment. See section
3c for the full grid.

A third follow-up (`sat_qk_sweep.sbatch`) fixes the winning MLP config
(`d_model=256, num_layers=4, dim_feedforward=1024`) and scans `nhead` and
`qk_dim` together -- `qk_dim` is the *total* (pre-head-split) Q/K
projection size, decoupled from `nhead`/`d_model` via
`spin_gnn.sat_transformer.LowRankSelfAttention` (V and the output
projection always stay at full `d_model`; only the key/query rank is
restricted or expanded). `nhead in {1,2,4,8,16}`, `qk_dim in
{64,128,256,512}` (256 = standard full rank; 512 is an over-complete Q/K
space larger than `d_model` itself) -- 20 grid points. **Result**: the new
overall best across every v1 sweep is `nhead=16, qk_dim=512` (accuracy
94.40%, NLL 4.76) -- the *first* config in this encoding to combine
top-tier accuracy with a nonzero `val_satisfying_completion_rate` (1.4%)
rather than trading one off against the other. The highest completion
rate in the grid (3.5%) instead shows up at the *smallest* `qk_dim=64`
(genuinely low-rank Q/K) paired with `nhead in {4,16}`, at lower accuracy
-- the accuracy/completion trade-off from the earlier sweeps isn't fully
gone, just no longer absolute. See section 3d for the full grid and
heatmaps.

A later diagnostic (`copy_vs_delta_breakdown`, run against this best v1
checkpoint -- see `scripts/_copy_vs_delta_probe.py`) explains *why*
`val_satisfying_completion_rate` stayed near zero despite 94% token
accuracy: teacher-forced per-dimension accuracy splits into 96.0% on
variables that are still unassigned (trivially "copy 0 forward") but only
**34.0%** on variables that are already decided (need to actually
remember/reproduce a specific committed value) -- barely above the 33%
chance rate for 3 classes, and the main reason this encoding motivated the
v2 rewrite below (see "v2: event-based reasoning-trace encoding").

`spin_gnn/ksat_render.py` also has `trace_to_lines` (one line per solver
step: the assignment, then every non-trivial clause, vs. `trace_to_text`'s
indented multi-line-per-step blocks) and `side_by_side_trace` (two such
line lists as aligned columns, e.g. a model-generated trace against the
true solver trace for the same instance -- see
`notebooks/sat_unit_propagation_results.ipynb` section 4's "Model-generated
trace vs. the true solver trace, side by side"). Since a freely
model-generated sequence has no externally-known step grouping the way a
real solver trace does, `trace_to_lines` falls back to
`infer_step_lengths`, which segments purely from the token stream's own
grammar (a step = one token plus any immediately-following clause-type
tokens) -- this reproduces the real step lengths exactly on a well-formed
trace, and degrades gracefully (rather than crashing) on a generated
sequence that doesn't follow the expected alternation.

`tests/test_ksat_solver.py` cross-checks `solve_with_trace`'s
satisfiable/unsatisfiable verdict against brute-force enumeration on small
random instances -- the correctness guarantee here, since there's no
closed-form reference the way `test_exact_recovery.py` has for SpinGNN.

## v2: event-based reasoning-trace encoding

The `copy_vs_delta_breakdown` result above motivated a second encoding of
the same underlying task (`spin_gnn/ksat2.py`, `ksat2_tokens.py`,
`sat_transformer2.py`, `train_sat_transformer2.py`): instead of re-emitting
the *entire* clause database at every step (v1's encoding, extremely
redundant -- most of each step's tokens are an unchanged copy of the
previous step's), only emit **events**: which single variable got set or
unset, and why. Every token is a single categorical id into a small fixed
vocabulary (standard `nn.Embedding` input, not v1's real-valued vectors),
rather than a vector-per-token.

**Grammar** (12 special tokens + one token per variable + one per clause):

```
BEGIN_HINTS   (VAR (TRUE|FALSE))*
BEGIN_STATEMENT   (CLAUSE_c (NOT? VAR)*)*                for c in 0..m-1
BEGIN_REASONING   ((NO_UNIT | IS_UNIT CLAUSE_c) SET VAR (TRUE|FALSE) | BACKTRACK VAR)*
SAT (VAR (TRUE|FALSE))*   |   UNSAT
```

`solve_with_reasoning_trace` (`ksat2.py`) is the same textbook DPLL as v1
(chronological backtracking, MCV branching), instrumented to additionally
track **which clause** triggers each unit-propagation (v1's solver found
the forced literal but discarded the clause index) and to emit an explicit
`unassign` event for *every* variable undone during a backtrack, not just
the final "give up on this decision level" pop -- v1's full-snapshot
encoding didn't need these (an unassignment was invisible bookkeeping,
since the whole state was recomputed from scratch every step); an
event-based encoding has to say it out loud. `hints` (`sample_hints`,
`SATReasoningConfig.n_hints`) are a partial assignment fixed *before* any
decision is made -- given facts, never touched by backtracking -- though
every sweep below uses `n_hints=0`.

**Does it actually solve the problem?** `sat_transformer2.solve_rate`
prompts the model with only hints + the problem statement (nothing about
*how* to solve it), lets it freely generate its own entire reasoning trace,
and checks whether the result is verifiably correct -- a strictly harder,
more meaningful bar than v1's teacher-forced `val_satisfying_completion_rate`.

**Findings, in order** (`spin_gnn/sat2_hparam_sweep.py`,
`scripts/slurm/sat2_hparam_sweep.sbatch` + follow-ups below, all at
`n_vars=16, alpha=1.25` -> `m_clauses=20`, "O(20) clauses" as a
deliberately easy/underconstrained starting regime):

1. A 72-config grid (`d_model x nhead x num_layers x lr`) found a best
   `solve_rate` of only 6.7% (`d_model=128, nhead=2, num_layers=2,
   lr=3e-4`) -- but already a real improvement in kind over v1: a 10-epoch
   smoke test hit 81% SAT/UNSAT-call accuracy, something v1 never
   approached at any epoch count.
2. A dedicated depth x LR scan (`sat2_layer_scan.sbatch`, `num_layers in
   {1,2,3,4,6,8,12,16}`) found `num_layers=16, lr=3e-4` best (7.0%), but
   `num_layers in {12,16}` at `lr=1e-3` **collapsed completely** (0%
   well-formed output) -- the classic post-norm-at-depth instability.
3. Adding `norm_first=True` (pre-norm: `x = x + Sublayer(LayerNorm(x))`,
   keeping the residual stream itself un-normalized, vs. post-norm's
   `x = LayerNorm(x + Sublayer(x))`) to `SATReasoningTransformer` and
   re-running the same grid (`sat2_prenorm_depth_scan.sbatch`, extended to
   `num_layers=24`) fixed the collapse everywhere (>=99.3% well-formed)
   *and* raised the best `solve_rate` to **12.3%** (same point,
   `num_layers=16, lr=3e-4`) -- the depth "ceiling" in step 2 was partly an
   optimization artifact, not a true capacity limit. `num_layers=24` did
   not beat 16 (not simply "deeper is better").
4. A head-count scan at that optimum (`sat2_prenorm_nhead_scan.sbatch`,
   `nhead in {1,2,4,8,16,32}`) found `nhead in {1,2}` best, declining as
   head count grows -- unlike depth, head count was never the lever, in
   either encoding. A repeat run at the identical `nhead=2` config landed
   at 4.0% vs. step 3's 12.3%, a reminder that single-run comparisons at
   this scale carry real noise (roughly 2-3x).
5. A `copy_vs_delta`-style per-role accuracy breakdown on the step-3
   checkpoint (`scripts/_sat2_step_accuracy_probe.py`) found the bottleneck
   is **which variable to act on**, not value prediction: 35% accuracy
   choosing which variable to backtrack on (n=40), 42% choosing which
   variable to branch on (n=2057) -- vs. 96-100% for the *value* to assign
   once a variable is chosen, and 72% for which step type (decide /
   propagate / backtrack) comes next. Motivated (but not yet implemented)
   a `[SATISFIED]`/`[REACTIVATED]` clause-status annotation to offload the
   implicit clause-bookkeeping burden from attention.

`notebooks/tokenization_comparison.ipynb` compares v1 vs. v2 training
curves directly (with explicit unit-normalization caveats, since v1's loss
sums cross-entropy over `n_vars+1` dimensions per token while v2's is a
single categorical cross-entropy). `notebooks/exploration_summary.ipynb`
is a 2-page writeup of the whole investigation (both encodings) with
citations to the exact sweep CSV/checkpoint/probe-output backing every
number above.

`tests/test_ksat2.py` and `test_ksat2_tokens.py` cover the event-stream
invariants (every unit-prop is actually unit when claimed, the event
stream replays to a consistent assignment history, hints are never
touched by backtracking) and the encode/decode round-trip (tolerant of
malformed/truncated input, since `decode` is also used on freely
model-generated sequences). `test_sat_transformer2.py` and
`test_train_sat_transformer2.py` cover the model/training pipeline,
including the `norm_first` checkpoint round-trip.

```
  slurm/run_tests.sbatch                  full pytest suite
notebooks/
  results.ipynb                        kinetic-Ising results: SpinGNN vs. parameter-matched SpinTransformer
  sat_unit_propagation_results.ipynb   v1 sweep results, sections 1-4 + 3b/3c/3d follow-ups

```

Note: `train.py`/`sparsify.py` regenerate their disorder realizations and
trajectories in-memory from a seed (deterministic, cheap for the sizes here)
rather than reading `generate_data.sbatch`'s saved `.npz` files -- that
standalone script is for separately inspecting/validating the physics (e.g.
checking equilibration, coupling statistics) outside the training loop.

## Running on Sherlock

This repo follows cluster policy: no Python/pip on the login node, all job
I/O on `$SCRATCH`, module versions verified with `ml spider` (already checked
at write time: `py-torch-geometric` has no Sherlock module, so it's pip
-installed into a venv on top of the module-loaded `py-pytorch/2.4.1_py312`).
The venv itself also lives on `$SCRATCH` (`setup_env.sh`), not `$HOME` or
`$GROUP_HOME` -- both were near their quota when this was written.

```bash
# one-time setup, from an interactive allocation:
sh_dev -c 4 -m 16G
bash scripts/setup_env.sh

# generate + inspect a few disorder realizations (CPU, cheap):
sbatch scripts/slurm/generate_data.sbatch

# train a single model:
sbatch scripts/slurm/train.sbatch --keep-prob 0.1

# sparsification sweep:
sbatch scripts/slurm/sparsify_sweep.sbatch

# context-length / data scaling sweep (array job, sganguli partition, low priority):
sbatch scripts/slurm/scale_sweep.sbatch
python -m spin_gnn.aggregate_scaling "$SCRATCH/spin_gnn/scale_sweep/power1"  # once all tasks finish

# AMP teacher-student reconstruction-error sweep over alpha=T/N:
sbatch scripts/slurm/amp_sweep.sbatch

# k-SAT unit-propagation statistics (CPU, cheap):
sbatch scripts/slurm/sat_stats.sbatch

# train the v1 (full-snapshot) SAT-trace transformer:
sbatch scripts/slurm/sat_train_transformer.sbatch

# v1 SATTransformer hyperparameter sweeps (GPU, sganguli partition):
sbatch scripts/slurm/sat_hparam_sweep.sbatch    # (d_model, nhead)
sbatch scripts/slurm/sat_nhead_sweep.sbatch     # nhead alone, fixed d_model=256
sbatch scripts/slurm/sat_mlp_sweep.sbatch       # (num_layers, dim_feedforward), fixed d_model/nhead
sbatch scripts/slurm/sat_qk_sweep.sbatch        # (nhead, qk_dim), fixed d_model/num_layers/dim_feedforward
python -m spin_gnn.aggregate_sat_sweep "$SCRATCH/spin_gnn/sat_hparam_sweep"  # once all tasks finish

# v2 (event-based) SATReasoningTransformer sweeps (GPU, sganguli partition):
sbatch scripts/slurm/sat2_hparam_sweep.sbatch        # (d_model, nhead, num_layers, lr), 72 configs
sbatch scripts/slurm/sat2_layer_scan.sbatch          # num_layers x lr, post-norm
sbatch scripts/slurm/sat2_prenorm_depth_scan.sbatch  # same grid, norm_first=True (fixes depth collapse)

python -m spin_gnn.aggregate_sat2_sweep "$SCRATCH/spin_gnn/sat2_hparam_sweep"  # once all tasks finish

# re-execute a results notebook in place after new sweep data lands:
sbatch scripts/slurm/build_sat_notebook.sbatch notebooks/exploration_summary.ipynb

squeue --me
```

To scale toward the paper's `N=5000`, raise `--n-spins`, but note the dense
`keep_prob=1.0` graph is `O(N^2)` in memory (`graph.py` uses a dense mask) --
for `N` much beyond a few thousand, sample edges directly instead of
materializing the full mask, especially at small `keep_prob`.
